# Game Tracker

صفحة مستقلة: `/game-tracker`، عبر تسجيل الدخول الحالي. يظهر رابط القائمة فقط للحسابات المصرح لها.

## إعداد الحسابات الأربعة

1. راجع `server/game-tracker.env.example`، واضبط المتغيرات الثمانية في `server/.env` أو بيئة تشغيل أمر الإعداد: إيميل وكلمة مرور مستقلان لـ Saif وAccountant 1 وAccountant 2 وAccountant 3.
2. استخدم إيميلات صحيحة ومختلفة، وكلمات مرور فريدة لا تقل عن 12 حرفًا ولا تتجاوز 72 بايت UTF-8. لا توجد كلمات مرور افتراضية. لا تضع القيم في source code أو Git.
3. من جذر المشروع شغّل `npm.cmd run setup:game-tracker --prefix server` (أو `npm run setup:game-tracker --prefix server` خارج PowerShell).
4. سلّم بيانات كل حساب لصاحبه عبر وسيلة آمنة. يمكنك إزالة كلمات المرور الأولية من البيئة بعد الإعداد؛ تسجيل الدخول يعتمد على bcrypt hashes في قاعدة البيانات.

الإعداد يتحقق من اكتمال المتغيرات وتميّزها قبل الاتصال أو الكتابة. لا يستبدل حسابًا قديمًا بمجرد تطابق الإيميل، ولا يغيّر كلمات المرور عند إعادة تشغيله. إذا كان إيميل مطلوب مستخدمًا بالفعل، يتوقف للمراجعة بدل منح صلاحية لحساب غير مقصود. لا تشغّل seed الرواتب لهذا الغرض.

الحسابات تنشأ بدور `staff` الحالي، مع صلاحيات إضافية للموديول فقط؛ لا يمنح الإعداد دور admin. النظام يحتفظ بصلاحيات بقية الصفحات كما كانت.

## الصلاحيات

أربعة مواضع ثابتة في `User.gameTrackerIdentity`: `saif`, `accountant1`, `accountant2`, `accountant3`. فهرس unique جزئي يمنع إسناد الموضع لأكثر من حساب. لا يحصل المستخدم على الصلاحية بسبب اسمه أو دوره العام، ولا تقبل registration API حقول صلاحيات من العميل.

- `game_tracker_access`: مفعلة للأربعة.
- `game_tracker_create`: مفعلة لـ Saif فقط؛ الباك إند يشترط أيضًا موضع `saif` عند الإنشاء.
- أي حساب آخر، بما فيه admin، لا يملك وصولًا افتراضيًا.

## API والبيانات

- `GET /api/game-tracker`: قراءة السجلات، مع `page` (افتراضي 1)، `limit` (افتراضي 20، أقصى 100)، `search` للاسم أو الإيميل أو المنتج، `date` كتاريخ محدد، `state` و`paymentMethod`.
- `POST /api/game-tracker`: إنشاء فقط، بواسطة Saif.
- `GET /api/game-tracker/:id/photos/:kind`: الصورة المحمية؛ kind هو `photoForPayment` أو `photoFromUs`.

لا توجد PUT/PATCH/DELETE endpoints. الطلبات بهذه الطرق من مستخدم مصرح تُرفض بـ405؛ غير المصرح يحصل على403، وبدون جلسة يحصل على401. الموديل يمنع إعادة حفظ مستند موجود، والتعديل والاستبدال والحذف عبر query middleware، وbulkWrite. لا توجد أعمدة أو أزرار تعديل/حذف في الواجهة.

حقول POST: `date`, `user`, `email`, `product`, `cost`, `price`, `state`, `website`, `paymentMethod`، وصورتان اختياريتان `photoForPayment` و`photoFromUs` بالشكل `{name, base64}`. لا يسمح بإرسال createdBy أو created_at؛ يضيفهما السيرفر تلقائيًا. المبالغ بالجنيه المصري وتخزن كقروش صحيحة. الموقع نص يُعرض دون تفسير HTML أو تنفيذ روابط.

الصور PNG/JPG فقط، حتى3 MB لكل صورة، وتخزن كـBuffer داخل MongoDB. يتحقق السيرفر من الحجم والتوقيع الثنائي بدل الوثوق بامتداد أو MIME يرسله العميل. لا يوجد مجلد uploads عام؛ الصور تُعرض بصلاحية موثقة، مع nosniff وCSP sandbox وprivate/no-store. استجابة القائمة لا تحتوي بيانات الصور الثنائية أو كلمات مرور.

السجلات مستقلة عن فترات الرواتب؛ تغيير فترة الرواتب لا يغيّر فلاتر Game Tracker. State نهائية ضمن السجل: حتى Pending لا تتغير بعد Save. أي عملية لاحقة تُسجل كسجل جديد.

الحماية هنا على مستوى التطبيق وMongoose. صاحب صلاحيات إدارة MongoDB يستطيع تغيير قاعدة البيانات مباشرة خارج التطبيق؛ عند النشر الذي يتطلب حماية من أدوات قواعد البيانات نفسها، استخدم صلاحيات MongoDB مخصصة تمنح find/insert فقط على collection `gametrackerrecords`، مع نسخ احتياطية محمية. لا يوجد كود اتصال ثانٍ أو تغيير لصلاحيات قاعدة البيانات القائمة ضمن هذا التعديل.

## التحقق

- `npm test --prefix server`: اختبارات الصلاحيات، رفض التعديل والحذف، الملفات، الحقول والفلاتر، بالإضافة لاختبارات النظام الحالية.
- `npm run build --prefix client`: بناء Angular.
- `node .verification/game-tracker-ui.mjs`: اختبار Edge ببيانات API وهمية للأدوار الخمسة (Saif، المحاسبون الثلاثة، مستخدم غير مسموح). يحتاج مسار Playwright المحلي المبين في السكربت.

اختبارات HTTP والمتصفح تستخدم بيانات اختبار منفصلة ولا تثبت حفظ سجلات فعلية في قاعدة بيانات التشغيل. تشغيل الإعداد يتطلب بيانات الحسابات الحقيقية في البيئة. لا توجد أوامر lint معرفة في package.json الحالي.
